# 압축 비밀번호·분할 압축

CLAUDE.md의 File Operations 절에서 나눈 규칙이다.

- 압축 비밀번호: 압축은 비밀번호를 받으면 파일 항목을 AES-256으로 암호화한다(ZIP은 이름을 암호화하지 않는다). ZIP 읽기·쓰기는 zip4j 하나로 한다. 압축 해제는 암호화된 항목을 만나면 압축 파일마다 따로 묻고(`ArchivePasswordProvider` → 작업 질문함, 아카이브마다 `ArchivePasswordSession`), 비밀번호는 출력을 만들기 전에 내용이 있는 가장 작은 암호화 항목(`passwordCheckEntryOf`, ZIP·RAR 공통 — 0바이트 항목은 풀 내용이 없어 비밀번호를 가리지 못한다)을 끝까지 풀어 보아 확인한다 — 검증값(AES 2바이트, ZipCrypto 1바이트)만으로는 틀린 비밀번호가 통과할 수 있어서다. 확인하는 동안은 `IndeterminatePhase.CheckingPassword`로 진행을 보고하고 그 보고에서 취소를 확인한다(`ArchivePasswordSession.reportChecking` — ZIP은 읽기마다, RAR은 기록·`setCompleted`마다, #418) — solid RAR은 확인할 항목 앞의 항목을 출력 없이 끝까지 풀어 오래 걸릴 수 있어서다. 같은 이유로 solid RAR 추출에서 건너뛴 항목을 푸는 동안에도 `setCompleted`마다 지금 진행을 다시 보고한다(`ByteProgressTracker.reportCurrent`). 목록 암호화 RAR을 열 때의 재시도는 헤더만 읽으므로 보고하지 않는다. 틀리면 '틀렸습니다'(검증값 불일치)나 '틀렸거나 손상'(내용 검증 실패 — RAR4·ZipCrypto는 틀린 비밀번호와 손상을 구분할 수 없다)으로 다시 묻고, 끝내는 길은 취소·무응답뿐이다. 확인한 비밀번호는 그 압축 파일 안에서만 다시 쓴다. 한 압축 파일 안에서 항목마다 다른 비밀번호는 ZIP·RAR 모두 지원 범위 밖이다 — 확인한 비밀번호가 맞지 않는 항목은 다시 묻지 않고 풀 수 없는 항목으로 실패한다. RAR의 목록 암호화는 열 때 묻는다. ZIP 항목 이름은 UTF-8로만 읽으며, 해석하지 못한 이름(U+FFFD)이 있으면 아무것도 풀지 않고 실패한다.
- 분할 압축: 형식마다 시작 볼륨으로만 푼다 — RAR `이름.part1.rar`(0을 앞에 붙인 번호 포함)과 옛 방식 `이름.rar`(+`.r00` …), ZIP `이름.zip`(+`.z01` …, 내용 목록이 이 마지막 볼륨에 있다)과 번호 분할 `이름.zip.001`(zip4j가 알아보는 소문자 확장자만), 7z 번호 분할 `이름.7z.001`. 이름의 역할(시작 볼륨/다른 볼륨)과 세트는 추출기의 `ArchiveExtractor.nameRoleOf`(규칙은 `ArchiveVolumeNames.kt`)가 이름으로만 정한다. 압축 해제 메뉴는 선택이 아카이브 하나로 묶일 때만 뜬다(`LocalFileOperationUseCase.canUnzip` → `FileActionRepository.extractionTargetOf`): 단일 아카이브·시작 볼륨 하나, 또는 다중 선택에서 시작 볼륨과 같은 폴더·같은 세트의 다른 볼륨들. 실행(`LocalArchiveExtraction.unzip`)도 같은 묶기로 세트를 시작 볼륨으로 한 번 풀고, 시작 볼륨 없이 받은 다른 볼륨은 지원하지 않는 형식으로 아무것도 풀지 않고 실패한다. 저장소 계약은 아카이브 하나만 받는다 — 아카이브 둘 이상(또는 없음)으로 묶이는 경로는 부르는 쪽의 계약 위반이라 아무것도 풀지 않고 `IllegalArgumentException`으로 거부한다(#429, 여러 아카이브를 한 번에 푸는 것은 지원 범위 밖). 볼륨은 모두 시작 볼륨과 같은 폴더에 있어야 한다. 아카이브 폴더 이름은 볼륨 번호와 확장자를 뺀 이름이다. 빠진 볼륨은 알아챈 때에 `FailureReason.MissingArchiveVolume`(`MissingArchiveVolumeException`)으로 실패한다: ZIP과 7z 번호 분할은 열 때 확인해 아무것도 풀기 전에(PKWARE 분할은 zip4j가 내용 목록으로 계산한 볼륨, 번호 분할은 이어지는 번호 뒤에 더 큰 번호가 있으면), RAR은 7-Zip이 요청한 볼륨이 없었는데 열지 못했거나 연 아카이브가 오류(ERROR·ERROR_FLAGS)를 알릴 때 — 7-Zip은 세트의 끝에서도 다음 이름을 물을 수 있어 요청만으로는 실패로 보지 않는다. 번호 분할의 마지막 볼륨이 빠진 것은 이름으로 알 수 없어 손상된 아카이브로 실패한다. 7-Zip 계열은 입력을 읽다 난 실패(기기 입출력 실패, 읽는 중에 줄어든 파일 — `FailureReason.ArchiveChangedWhileReading`)를 입력이 보관해(`SevenZipInput.readFailure`), 라이브러리가 그 실패를 감싸 알려도 원래 실패로 끝낸다 — 형식을 지정해 열 때 "이 형식이 아님"(`UnreadableArchive`)으로 보지 않는다. 비밀번호를 받아 다시 열 때의 실패는 지금처럼 '틀렸거나 손상'으로 다시 묻는다. 지원 범위 밖: 이름이 `*.part2.rar`인 단일 아카이브, 옛 방식 RAR의 `.r99` 다음 볼륨(`.s00` …), 안쪽 형식을 알 수 없는 `이름.001`, 대소문자만 다른 볼륨 이름(같은 세트로 묶지 않는다).
- 압축 파일 안의 링크 항목(심볼릭·하드 링크)은 지원 범위 밖이다(#424): 만들지 않고 `ArchiveEntryWriter.skipLink`로 건너뛰어 `FailureReason.UnsupportedLink`로 알린다(나머지 항목은 계속 푼다, 진행률에서는 처리한 파일로 넘긴다). 그대로 풀면 링크 대상 경로를 내용으로 한 파일이나 빈 파일이 성공으로 남기 때문이다. 판별은 라이브러리가 알리는 속성으로만 한다 — ZIP은 외부 속성 위쪽 16비트의 Unix 모드(`isZipSymlink`, 만든 시스템은 보지 않는다), 7-Zip 계열은 `SYM_LINK`·`HARD_LINK`(RAR5, ISO Rock Ridge)·`POSIX_ATTRIB`(ISO Rock Ridge)·0x8000 표시와 함께 `ATTRIBUTES` 위쪽 16비트에 담은 Unix 모드(p7zip이 만든 7z)(`isSevenZipLink`). 링크 정보를 알리지 않는 형식의 링크(RAR4의 Unix 링크, UDF)는 판별할 수 없어 지원 범위 밖이며 일반 파일로 풀린다. RAR5의 복사 링크는 라이브러리가 가리키는 파일의 내용으로 풀므로 링크로 보지 않는다. 7-Zip 계열의 판별은 속성 값 단위 테스트로만 검증했다(라이브러리는 JVM에서 열 수 없다, 기기 확인은 #435).
- 내용 보기(보기 자체는 압축 파일을 바꾸지 않는다 — 바꾸는 것은 아래 압축 파일에 추가뿐이다): 로컬 목록·검색 결과에서 내용을 볼 수 있는 압축 파일(압축 해제와 같은 이름 규칙의 단일 아카이브·시작 볼륨, `ArchiveContentRepository.canView`)을 누르면 다른 앱 대신 내용 보기 화면(`ARCHIVE_VIEW`, `ArchiveViewViewModel`)을 연다. 분할 압축의 다른 볼륨은 지금처럼 다른 앱으로 넘긴다. 원격 압축 파일은 지원 범위 밖이다. 목록은 추출기의 `ArchiveExtractor.entries`(압축 해제의 크기 계산 `ArchiveExtractor.measure`와 같은 순회·종류·크기 판별. 크기 계산은 종류와 크기만 읽어, 내용 보기가 표시하려고 읽는 값(수정 시각·암호화 여부)이 압축 해제에 영향을 주지 않는다)로 내용을 풀지 않고 화면을 열 때 한 번 읽고, `archiveTreeOf`가 폴더 트리로 만든다: 위치는 압축 해제(`ExtractionRoot.targetOf`)와 같은 판정 함수(`extractionSegmentsOf` — 빈 세그먼트·`.` 무시, `..`는 앞 세그먼트를 지움)로 정한다. 판정은 항목 경로만 보아, 절대 경로와 `..`로 루트 위로 올라가는 경로는 다시 들어와도(`../<풀 폴더 이름>/x`) 압축 해제도 풀 폴더와 상관없이 풀 수 없는 경로로 건너뛴다 — 풀 폴더에 붙여 정리하면 같은 항목이 풀 폴더 이름에 따라 풀리거나 건너뛰고, 풀 폴더를 모르는 내용 보기와 판정이 어긋나므로. 폴더 항목이 없는 형식은 경로로 폴더를 만들고, 같은 이름의 폴더는 합치고 파일은 이름이 같아도 모두 둔다. 압축 해제 위치 밖이나 루트 자신을 가리키는 항목은 숨기지 않고 루트에 원래 경로로 "풀 수 없는 경로"로 보인다. 링크·암호화된 파일은 그 표시와 함께 보인다. 읽지 못하면(지원하지 않는 이름, 손상, 빠진 볼륨, UTF-8이 아닌 ZIP 이름) 빈 목록이 아니라 실패와 다시 시도를 보인다. 비밀번호는 목록 암호화 RAR을 열 때만 묻는다(내용만 암호화한 항목은 묻지 않는다) — 이 질문은 작업이 아니라 화면의 읽기에 묶여 있어 작업 질문함이 아니라 `ArchiveViewViewModel`이 같은 `ArchivePasswordDialog`로 묻고, 틀리면 다시 묻고, 취소하면 화면을 닫는다. 정렬은 파일 목록의 정렬 기준(`SortMode`, `SortableEntry`)을 그대로 쓴다. 길게 눌러 끌면 파일 목록과 같은 부품(`dragSelectGesture`, `SelectAllBar` — 다중 선택 중에는 이름 자리 위에 겹쳐 그려 목록을 밀지 않는다)으로 다중 선택한다. 선택은 이름이 아니라 항목 키(`ArchiveEntryKey` — 파일·링크·풀 수 없는 경로는 항목 목록에서의 순번, 폴더는 이름)로 들어, 이름이 같은 파일도 따로 고르고 정렬이 바뀌어도 이어진다. 키는 한 폴더 안에서만 항목마다 다르다(같은 이름의 폴더는 합쳐 있다) — 폴더 밖에서 키를 쓰는 쪽은 그 폴더의 위치를 따로 갖는다. 다중 선택은 지금 폴더 안에서만 한다(파일 목록의 #519와 같은 규칙: 행을 누르면 토글하고 뒤로가기는 선택만 비운다). 키는 한 번 읽은 목록 안에서만 뜻이 있어, 목록을 다시 읽으면 다중 선택을 끝낸다. 항목 열기는 지원 범위 밖이다.
- 고른 항목 복사: 내용 보기의 다중 선택 중 복사를 누르면 고른 항목(`ArchiveEntrySelection` — 압축 파일, 지금 폴더, 키, 목록 식별값)을 로컬 화면의 압축 파일 항목 복사 대기(`SelectMode.ArchiveCopy`, `selection-state.md`의 `Receiving`)로 넘기고 내용 보기를 닫는다(떠나는 입력이라 선택을 꺼내기 전에 RESUMED를 확인한다). 로컬 목록에서 목적지를 고르고 '여기에 복사'를 누르면 `ArchiveCopyUseCase` → `ArchiveEntryCopyRepository.extractEntries`(구현 `LocalArchiveExtraction.extractEntries`)가 고른 항목만 고른 폴더 기준의 상대 위치로 푼다(`FileOperationType.ARCHIVE_COPY`, 표시 문구는 복사와 같다). 고른 항목은 내용 보기 트리와 같은 판정으로 찾는다(`selectedEntryPathsOf` — 폴더 키는 그 아래 항목 전체, 루트에서 고른 풀 수 없는 경로는 원래 경로로 넘겨 압축 해제처럼 실패로 알린다). 추출기는 받은 범위(`ExtractionScope` — 전체 압축 해제는 `Whole`) 안의 항목만 세고 풀며, 비밀번호 확인에 풀어 볼 항목도 범위 안에서 고른다 — 고른 항목에 암호화된 것이 없으면 묻지 않는다. 충돌·폴더 합치기·공간 검사·링크·비밀번호 질문은 압축 해제와 같다. 키는 목록 순번이라 그사이 압축 파일이 바뀌면 같은 키가 다른 항목을 가리킨다 — 그래서 풀기 전에 지금 목록의 식별값(`listingIdOf`, 항목마다 순서·경로·종류·크기·수정 시각·암호화 여부를 넣은 SHA-256)을 내용 보기가 읽은 값과 비교해, 다르면 아무것도 풀지 않고 `FailureReason.ArchiveChangedSinceViewed`로 실패한다. 식별값을 비교한 뒤 크기 계산·풀기가 압축 파일을 다시 여는 사이에 파일이 바뀌는 경우는 막지 않는다(지원 범위 밖 — 전체 압축 해제의 크기 계산과 풀기 사이와 같은 틈이다). 고른 항목만 풀 때 7-Zip은 solid 블록 안의 고르지 않은 항목도 건너뛰며 풀어 그 결과를 알리므로, 그 결과가 오류면 실패는 그 항목의 아카이브 안 경로를 가리킨다(`SevenZipExtractCallback`). 이 대기는 로컬 압축 파일만 읽으므로 원격 세션이 끊겨도 남는다.
- 압축 파일에 추가(ZIP만): 로컬 다중 선택의 더보기 '압축 파일에 추가'로 추가할 곳을 찾는 모드(`SelectMode.AddToArchive`, `selection-state.md`)에 들어가면, 로컬 목록에서 폴더는 열고 파일은 내용을 볼 수 있는 압축 파일만 내용 보기로 연다(`ItemClickAction.OPEN_ARCHIVE` — 다른 파일을 외부 앱으로 열지 않는다). 내용 보기는 넣을 수 있는 압축 파일(`ArchiveAddUseCase.canAddTo` — 이름이 단일 `.zip`)이고 목록을 다 읽었을 때, 다중 선택이 아니면 '여기에 추가'를 겹쳐 그린다. 확인하면 로컬 선택을 꺼내(`submitArchiveAddSelection` — 그사이 다른 작업·전송으로 바뀌었으면 꺼내지 않는다) `ArchiveAddRepository.addFiles`(구현 `ZipArchiveAppend`)가 지금 폴더에 넣는다(`FileOperationType.ARCHIVE_ADD`). 화면은 닫지 않고, 끝나면 내용 보기와 로컬 목록을 다시 읽는다. 확인은 화면을 떠나지 않으므로 RESUMED를 확인하지 않는다(연타한 두 번째 확인은 꺼낼 선택이 없다).
  - 원본은 건드리지 않는다: 같은 폴더의 임시 사본에 넣고 장치에 기록(`forceToDisk`)한 뒤 `replaceFileAtomically`로 원본 자리에 바꾼다. 실패·취소하면 임시 사본만 지운다(`deletingUnlessCompleted`). 완료 보고(취소 확인)는 교체 전에 한다 — 교체한 뒤의 취소가 바뀐 압축 파일을 취소로 알리지 않도록. 같은 압축 파일에 대한 앱의 추가는 원본을 읽는 데서부터 교체까지 차례로 실행한다(정규 경로별 잠금, `KeyedMutex` — 겹치면 뒤에 교체한 사본이 앞의 추가가 넣은 항목을 지운다). 충돌 판정도 잠금 안에서 해, 뒤의 추가는 앞의 추가의 결과로 묻는다. 기다리는 동안 진행 표시는 시작 상태에 머물고 취소하면 기다림을 끝낸다. 사본을 만든 뒤 교체하기 전에 다른 앱이 원본을 바꾸면 그 변경은 교체로 사라진다(지원 범위 밖 — 파일 시스템에 잠금이 없다).
  - 넣을 항목은 압축과 같은 수집(`collectArchiveSources` — 링크·안을 읽지 못한 폴더는 넣지 않고 실패로 알린다)으로 모은다. 넣을 항목에 그 압축 파일 자신이 있으면(고른 항목이거나 고른 폴더 안) 바꾸지 않고 `FailureReason.ArchiveAddedIntoItself`로 실패한다.
  - 같은 이름은 쓰기 전에 모두 묻는다(`appendPlanOf` — 쓰기와 나눈 판정). 자리는 내용 보기와 같은 판정(`extractionSegmentsOf`)으로 정해 표기만 다른 이름(`./docs/a.txt`, `docs//a.txt`)도 같은 자리로 보고, 풀 수 없는 경로의 항목은 어느 자리와도 겹치지 않는다. 폴더끼리는 묻지 않고 합치고(폴더 항목 없이 경로에만 있는 폴더도 같다), 파일끼리는 묻고(진행하면 그 자리의 기존 항목을 모두 지우고 새 내용으로 바꾼다), 종류가 엇갈리면 건너뛰기만 할 수 있다(건너뛴 폴더의 안쪽도 넣지 않는다). 모두 건너뛰면 압축 파일을 다시 쓰지 않는다. 덮어쓸 기존 항목은 사본에서 한 번에 지운다 — zip4j가 사본 전체를 다시 써, 그동안은 진행을 보고하지 않고 취소는 지우기가 끝난 뒤 듣는다(지원 범위 밖). 공간 검사는 원본 크기(덮어쓰면 두 배) + 넣을 크기다.
  - 압축 파일에 암호화된 항목이 있으면 비밀번호를 묻고 기존 항목으로 확인한 뒤(`zipPasswordCheckEntryOf`·`checkZipPassword` — 압축 해제와 같다), 새 파일 항목도 그 비밀번호로 AES-256 암호화한다. 암호화된 항목이 없으면 묻지 않고 암호화하지 않는다.
  - 넣을 수 없는 압축 파일: RAR·ISO는 쓰기 라이브러리가 없고, 7z는 지원 범위 밖이며, 분할 ZIP은 zip4j와 규격이 수정을 받지 않는다. 이런 압축 파일의 내용 보기에는 '여기에 추가'를 보이지 않고, 저장소 계약도 `FailureReason.ArchiveNotAppendable`로 거부한다. PKWARE 분할의 내용 목록 파일(`.zip`)은 이름으로 가리지 못해 버튼은 보이며, 실행할 때 열어 보고 거부한다.
  - zip4j는 작업 안에서 난 예외(진행 보고가 던진 취소, 구현 오류, 입출력 실패)를 모두 `ZipException`으로 감싸므로, 추가는 감싼 원래 예외를 다시 던진다(`unwrappingZipTask`) — 그대로 두면 취소가 입출력 실패로 바뀐다.
