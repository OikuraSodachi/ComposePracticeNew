# FTP 규칙

원격(FTP) 구현과 테스트를 다룰 때 적용한다. 원격 연결 상태(`RemoteConnectionState`)는 루트 CLAUDE.md의 File Operations에 있다.

- FTP: 서버 응답 해석(명령별 예외 규칙 포함, 예: RMD 거부에 붙이는 숨김 항목 안내)은 `FtpReplyRules`에만 둔다. 목록 조회(LIST·MLSD)의 거부 응답(4xx·5xx)은 모두 조회 실패다 — 지원 범위는 빈 디렉터리에 빈 목록과 226으로 답하는 서버이며, 450(RFC 959의 일시 거부)을 빈 목록으로 보지 않는다(#259). 2xx로 끝난 빈 목록은 빈 폴더로 본다. 열지 못한 폴더를 2xx로 답하는 서버(vsftpd)는 응답 코드로 구분할 수 없고(실패는 응답 문구로만 드러나 서버별 해석이 필요하다 — 필요하면 별도 기능으로 제안한다), 그런 서버가 드러내지 않은 항목은 아래 목록 범위처럼 지원 범위 밖이다(#266). 그 폴더의 결과는 앱이 책임지지 않는다: 업로드는 묻지 않고 덮어쓰고, 폴더 다운로드는 빈 폴더로 완료를 보고하며, 재귀 삭제는 보이는 항목을 지운 뒤 RMD 거부로 끝난다(서버가 숨긴 항목과 같은 결과, `collectRemoteTree` KDoc). 데이터 연결을 쓰는 명령(LIST·MLSD·RETR·STOR)이 데이터 연결을 열기 전에 거부되면, 보낸 데이터 명령이 아니라 실제로 거부된 명령(준비 명령 PASV·EPSV·REST 포함)의 이름으로 알린다(`DataCommandOutcome.Refused.command`, `FtpReplyRules.dataCommandRefusal`, #268). commons-net은 거부 응답을 읽은 직후 null을 돌려주므로 마지막으로 보낸 명령(`FtpCommandClient.lastSentCommand`, commons-net의 명령 송신 이벤트로 기록)이 거부된 명령이다. `FtpSession.withConnectedClient`가 명령 실패의 의미를 정하는 유일한 경계다. 블록이 돌려준 결과는 세션 유지, 던진 IOException은 연결 끊김(세션 종료), 그 밖의 예외는 세션 종료 후 전파한다. 취소는 이 경계를 그대로 지나가므로, 취소 뒤의 정리 명령(`DataCommandRunner.cleanUpAfterCancel`)은 그 자리에서 같은 규칙을 따른다 — 거부는 결과, 응답을 읽지 못하면 세션 종료이며, 세션이 이미 끝났으면 보내지 않는다. 세션을 유지할 실패는 블록 안에서 던지지 말고 결과로 돌려준다. 명령·서버 동작 조합은 `FtpCommandContractTest` 행렬로 검증한다.
- FTP 연결: `FtpConnector.connect`는 로그인 후 `FtpListingFormat.isReadable`로 목록을 해석할 수 있는지 확인한다(MLSD 미지원 서버가 SYST를 거부하거나 해석기 없는 종류를 알려주면 불가). 불가면 형식을 추측하지 않고 연결을 종료해 `ConnectResult.Failed(LISTING_FORMAT_UNKNOWN)`을 돌려주며, app은 `ConnectFailureNotice`로 다이얼로그를 띄운다. 그래서 연결된 세션의 목록 조회는 해석기를 고르지 못해 실패하지 않는다.
- FTP 목록 범위: 목록은 서버가 드러내는 항목이다(RFC 3659 §7.1). 서버가 숨긴 항목(유닉스 계열 LIST의 `.` 항목 등)은 지원 범위 밖이며, LIST에 `-a` 같은 비표준 옵션(RFC 959에 없음)을 붙이지 않는다. 숨김 항목 표시가 필요하면 별도 기능으로 제안한다. LIST 서버의 목록은 디렉터리로 이동(CWD)한 뒤 인자 없는 `LIST`를 보낸다(`FtpCommandExecutor.listWithList`)(curl과 같은 방식) — LIST 인자를 옵션으로도 읽는 서버(ProFTPD 등)가 있어 경로 인자의 해석이 서버마다 갈릴 수 있다.
- FTP 목록 해석(#255): 목록 데이터는 commons-net `FTPListParseEngine.getFiles`로 해석하지 않는다 — 해석하지 못한 줄을 말없이 버려 항목이 빠진 목록을 성공으로 보고하고, 해석기가 값 때문에 던지는 예외(숫자가 아닌 size 등)는 목록 전체를 구현 오류로 실패시킨다. 해석기의 규칙으로 줄만 받고(`FtpListingFormat.readLines`) 줄마다 해석해(`FtpListingFormat.parsedEntry`), 해석하지 못한 줄(예외를 던진 줄 포함)은 `ListedItem.Unreadable`로 남긴다. 화면 목록은 읽은 항목만 보여 주고 뺀 줄 수를 목록 결과(`ListedDirectory.unreadableCount` → `DirectoryListing.Loaded.unreadableCount`)에 담는다(`FtpPathAwareFileSystem`). 이 수는 목록의 상태라 알림으로 넣지 않고(다시 조회할 때마다 쌓이므로, #348) 그 목록이 화면에 있는 동안 목록 위에 안내하며, 읽지 못한 줄만 있는 목록은 빈 폴더로 표시하지 않는다(`DirectoryListingContent`). 0이 아닌 목록은 불완전한 목록(`isComplete` = false)이라 이름 충돌 판정(업로드·이름 변경)에 쓰이지 않는다. 트리 수집을 쓰는 작업은 그 줄만 실패로 알리고 나머지를 처리한다 — 폴더 다운로드는 받지 못한 항목, 재귀 삭제는 지우지 못한 항목으로 알리고 그 줄을 품은 디렉터리는 RMD하지 않는다. 그 줄은 이름을 몰라 실패·진행 표시 이름에 받은 줄(앞뒤 공백 제외)을 쓰고(`ListedItem.failureName`, #347), 자리(건너뛴 폴더 안인지 판정)는 줄이 나온 디렉터리로 정한다(`ListedItem.locationPath`) — 표시 이름과 자리를 한 값으로 쓰면 여러 줄이 같은 폴더 이름으로만 보인다. MLSD의 심볼릭 링크 줄(`type=OS.unix=symlink`·`type=OS.unix=slink:<대상>`)은 commons-net이 해석하지 못하며(사실 값에 `=`가 또 있음), 링크는 지원 범위 밖이므로 따로 알아보지 않고 이 규칙으로 실패시킨다. 해석기가 버리는 줄은 해석기의 `preParse`가 정한 것뿐이다(Unix LIST의 영어 `total N` 등). 그 밖에 항목이 아닌 줄(빈 줄, 지역화된 `ls -l`의 `합계 N`)도 이 규칙으로 실패한다 — MLSD는 RFC 3659 §7.2 형식, LIST는 commons-net 해석기가 읽는 영어 출력만 지원 범위다(지역화된 LIST는 날짜도 지역화돼 항목 줄도 해석되지 않는다).
- FTP 현재 디렉터리: LIST 조회는 세션을 조회한 폴더 안에 남긴다(`FtpCommandClient.workingDirectory`, 이동은 기록과 묶인 `changeDirectory`로만 한다). 로그인 직후의 현재 디렉터리(PWD)는 `FtpCommandClient.homeDirectory`로 기록한다. 폴더를 지우거나 이름을 바꾸는 명령은 세션이 그 대상 안에 있으면 같은 잠금 안에서 먼저 대상 밖(상위 폴더, 거부되면 대상 밖의 홈)으로 CWD한 뒤 보낸다(`FtpCommandExecutor.leavingTarget`) — 현재 디렉터리의 삭제를 거부하는 서버(Apache FTP Server, Windows)를 위한 사전 조치이므로, 나가지 못해도 명령은 보내고 서버의 응답을 결과로 삼는다. 새 변경 명령도 이 규칙을 따른다. 목록에 서버가 숨긴 항목이 빠질 수 있어 클라이언트가 누락을 알 수 없으므로, RMD 거부 메시지에는 그 가능성을 덧붙인다(`FtpReplyRules.HIDDEN_ENTRIES_NOTE`).
- FTP 트리 수집(`FtpCommandExecutor.collectRemoteTree`, 폴더 다운로드·삭제): 수집이 끝나는지를 목록의 정확성에 맡기지 않는다. 끝나는 것은 메모리 상한이 보장한다 — 받은 목록의 추정 메모리(`TreeMemoryBudget`, 항목마다 170바이트 + 경로·이름 문자당 2바이트)가 32MiB를 넘으면 멈춘다. 목록 하나도 받는 동안 남은 상한을 넘으면(`BoundedListingStream`, 줄마다 250바이트 + 항목 경로의 앞부분(조회한 디렉터리 경로) 문자당 2바이트 + 받은 바이트당 4바이트로 추정 — 앞부분은 받은 데이터에 없어 세지 않으면 깊은 폴더의 큰 목록이 받은 뒤의 추정 전에 메모리를 바닥낸다. 줄 끝은 해석기(`BufferedReader.readLine`)와 같이 CR·LF·CRLF를 하나로 센다) 끝까지 받지 않고 데이터 연결을 중단으로 닫아 그 폴더의 실패로 끝낸다(세션 유지) — 항목이 아주 많은 폴더나 목록을 끝없이 보내는 서버에서 받은 뒤에 세면 그 전에 메모리가 바닥난다. 들어가 있는 디렉터리의 식별값(MLSD `unique`)은 추정에 더하지 않는다 — 주류 서버(ProFTPD·Pure-FTPd)의 값은 장치 번호·inode의 16진수(약 33자 이하)라 정상 트리에서는 실제 메모리가 상한을 조금 넘는 정도지만, RFC 3659의 `unique` 문법(`token = 1*RCHAR`)에 길이 상한이 없어 수 KB 이상의 `unique`를 보내는 서버에서는 깊이마다 쌓여 메모리가 바닥날 수 있다(`TreeMemoryBudget` KDoc). 화면 목록(`listFiles`)에는 이 상한이 없다. 방문한 디렉터리도 모두 받은 항목이므로 방문 수도 함께 막는다(#257). 지원 범위는 받은 목록이 이 상한 안인 트리이며, 넘는 트리는 순환이든 아니든 실패다. 서버가 MLSD `unique`(RFC 3659 §7.5.2)를 이미 목록에 담아 보내면, 하위 디렉터리 항목의 값이 거쳐 온 상위 디렉터리의 값과 같을 때 순환으로 보고 상한보다 일찍 알린다. `unique`를 담도록 요청하지 않으며(`OPTS MLST`), 자신 항목(`type=cdir`)의 값은 쓰지 않는다(#260). 순환 감지의 지원 범위는 같은 대상에 어느 경로로든 같은 `unique`를 주는 서버다(RFC 3659 §7.5.2) — 경로마다 다른 값을 주는 서버의 순환은 순환으로 알리지 못하고, 순환이 아닌 큰 트리와 구분할 수 없어 상한·경로 한도의 실패(판별 불가 설명 없음)로 끝난다. 경로가 PATH_MAX(4096바이트)에 이르면 식별값과 무관하게 멈춘다. 실패한 디렉터리까지의 경로(시작 디렉터리 제외, 실패한 그 디렉터리 포함)에 식별값 없는 디렉터리가 있으면, 상한·경로 한도의 실패 메시지에 판별할 수 없다고 덧붙인다 — 순환은 지금 경로 위에서만 일어나므로, 끝내고 나온 형제 디렉터리는 따지지 않는다. 어느 쪽이든 일부만 처리하지 않고 실패로 알린다. 상위가 아닌 폴더와 식별값이 같은 것(형제를 가리키는 링크)은 순환이 아니다. 폴더 수·시간 상한은 두지 않는다(순환과 큰 트리를 구분할 수 없어 정상 트리도 실패시킨다). 대신 받은 항목마다 준비 단계 진행을 보고하고 그 보고에서 취소를 받아, 멈출지는 사용자가 진행 다이얼로그의 취소로 정한다(#284). 삭제(`FtpCommandExecutor.delete`)는 고른 대상의 트리를 모두 모은 뒤 작업 전체의 항목 수 기준으로, 항목마다 명령 전에 진행을 보고한다.
- FTP I/O 상한: `FtpSession`이 클라이언트의 모든 소켓 읽기·쓰기 한 번에 같은 상한(15초)을 건다 — 제어 연결 읽기는 `defaultTimeout`, 데이터 연결 읽기는 `dataTimeout`, 쓰기는 `AbortableSocketFactory`가 만드는 `WriteBoundedSocket`(java.net.Socket에는 쓰기 제한 시간이 없다). 상한은 데이터가 하나도 오가지 않는 시간이며 전송 전체 시간이 아니다. 상한 값은 `FtpSession`의 `ioTimeoutMillis`(0보다 커야 한다)로만 정하며, 넘겨받은 client에 먼저 정한 값은 덮어쓴다. 데이터 연결은 수동 모드만 지원한다 — 능동 모드 데이터 소켓은 서버 소켓의 accept로 만들어져 상한·잠금 밖 종료를 받지 않으므로, `PassiveOnlyServerSocketFactory`가 열지 못하게 해 구현 오류로 실패시킨다. 쓰기 감시와 쓰기 완료가 겹치면 먼저 일어난 쪽만 결과를 정한다(`WriteDeadline`). 데이터 연결을 쓰는 명령(RETR·STOR·LIST·MLSD) 중 데이터 연결이 상한을 넘기면 데이터 소켓을 리셋으로 닫고 완료 응답을 읽어 그 항목(목록은 그 폴더)만 실패로 돌려준다(응답도 오지 않으면 세션 종료). PASV 뒤 데이터 소켓을 연결하지 못한 실패는 아래 데이터 소켓 연결 실패 항목을 따른다. 다른 곳에서 timeout을 따로 정하지 않는다.
- FTP 전송 중단: stream 모드에서 데이터 연결을 정상으로 닫는 것은 파일 끝이다(RFC 959 §3.4.1) — 중단을 같은 닫기로 알리면 서버는 잘린 업로드를 다 받은 파일로 저장한다. 그래서 데이터 연결을 쓰는 명령(전송·목록 조회)은 모두 `DataCommandRunner`로 실행한다 — 데이터 스트림을 `FtpSession.openDataConnection`으로 열어 `DataConnection`으로 다루고, 끝까지 주고받은 명령만 `finish`(정상 닫기)로, 실패·취소·구현 오류로 멈춘 명령은 `abort`(SO_LINGER 0, 리셋)로 닫은 뒤 완료 응답을 읽는다. commons-net의 `listFiles`·`mlistDir`는 데이터 실패와 완료 응답 실패를 같은 예외로 던지므로 쓰지 않고, 목록 데이터 스트림은 `SessionFtpClient`로 연다. 새 데이터 명령도 이 경로를 쓴다. 쓰기 상한 초과(`WriteBoundedSocket.abort`)와 잠금 밖 종료(`AbortableSocketFactory.closeAll`)도 리셋으로 닫는다. 정상 닫기가 실패한 것(남은 데이터를 보내지 못함)도 전송 실패다. 취소한 업로드(STOR)는 완료 응답을 읽은 뒤 받다 만 파일을 DELE로 지운다 — 중단된 STOR의 파일을 남길지는 RFC 959에 정함이 없어 서버마다 다르다. 지우지 못하면(거부, 세션 종료) 취소는 결과로 돌려줄 수 없으므로 `FtpTransferrer`가 이유를 담아 작업 메시지 알림함(`OperationNoticeReporter`)에 직접 넣는다.
- FTP 데이터 소켓 연결 실패(#267): 수동 모드 데이터 소켓을 서버가 알려준 주소에 연결하지 못한 실패(방화벽·NAT가 막은 경우 등)는 그 명령만의 실패(`IoResult.ItemFailed`)이며 세션을 유지한다. commons-net은 PASV 응답을 다 읽고 데이터 소켓을 연결한 뒤에야 명령을 보내므로(`FTPClient._openDataConnection_`) 그 시점의 제어 채널은 응답 순서가 맞다 — 이 전제는 `FtpDataConnectFailureTest`가 서버가 명령을 받지 않았는지로 고정한다. 판별은 `FtpSession.openDataConnection`이 실패한 명령이 만든 데이터 소켓이 하나도 연결되지 않았는지로 한다(`DataConnectionOpening.NotConnected`). 연결한 뒤의 실패(REST·명령의 응답, 원격 주소 확인)는 명령의 응답이 남았을 수 있어 세션 종료다. 잠금 밖 종료가 소켓을 닫아 연결하지 못한 경우도 세션이 끝난 것이므로 `DataCommandRunner`가 세션 상태를 보고 예외로 전파한다. 여러 항목 작업은 남은 항목을 계속 시도하며, 항목마다 연결 상한(`FtpConnector`의 `CONNECT_TIMEOUT_MS`)까지 기다린다.
- FTP 종료: FTPClient는 스레드에 안전하지 않으므로 ioMutex를 쥔 쪽만 명령을 보내고 `disconnect()`한다. 진행 중 I/O를 기다리지 않는 종료(`FtpSession.closeBypassingIoLock`)는 잠금 밖에서 소켓(`AbortableSocketFactory`가 만든 제어·데이터 소켓)만 닫는다 — 막힌 명령은 IOException을 받아 자기 잠금 안에서 정리하고, 진행 중인 명령이 없을 때만 종료 쪽이 잠금을 얻어 QUIT을 보낸다. 연결 작업과 겹친 종료 요청은 `FtpSession.markLoggedIn(closeMark)`가 종료 요청과 같은 잠금 안에서 확인해, 연결 작업이 어느 단계에서 끝났든 연결 성공으로 뒤집히지 않는다. 표지는 `beginConnecting`이 연결 작업 표시와 같은 잠금 안에서 읽어 돌려주며, `FtpConnector.disconnect`는 소켓이 아직 열리지 않았어도 연결 작업 중이면 종료를 요청한다. 앱이 연결을 더 유지할 수 없어 끝내는 종료(`FtpConnector.drop`, 시스템의 실행 시간 한도·서비스 시작 거부)는 연결된 세션만 같은 경로로 닫고 `Lost`로 남긴다(`FtpSession.dropConnected`) — 연결돼 있는지를 종료 기록과 같은 잠금 안에서 판단해, 연결 작업 중인 새 연결을 끝내거나 이미 끊긴 세션의 `Lost`를 덮어쓰지 않는다. 끝냈는지를 돌려주며, 끝낸 연결이 있을 때만 알린다.
- FTP 전송의 같은 이름(#316): STOR는 같은 이름의 원격 파일을 덮어쓰고, "지정한 이름으로, 없을 때만 만들기"를 보장하는 표준 명령이 없다(STOU는 서버가 이름을 정한다 — RFC 959, RFC 1123 §4.1.2.9). 그래서 업로드 충돌은 확인할 때의 목록으로만 판정하며(`ConflictCheckUseCase`), 그 뒤 서버에 생긴 같은 이름의 파일을 덮어쓰는 틈과, 열지 못한 폴더를 2xx 빈 목록으로 답하는 서버에서 목록에 드러나지 않은 항목을 덮어쓰는 것(첫 항목, #266)은 지원 범위 밖이다. 다운로드는 로컬에 쓰므로 쓰는 시점에 파일 시스템 결과로 판정한다 — 로컬 파일·폴더 자리는 세션 잠금 밖에서 확보하고(`FtpTransferrer.claimLocalFile`·`claimLocalDirectory`, 답을 기다리는 동안 ioMutex를 쥐지 않도록), 덮어쓰기로 한 기존 파일은 서버가 전송을 받아들인 뒤에 연다. 받기 시작하지 못하면 이 다운로드가 만든 빈 파일만 지운다(`receivingInto`).
